## 一、技术方案设计

### 1. 如何编写一份技术方案文档？

**技术方案文档结构：**

```markdown
# [项目名称] 技术方案

## 1. 背景与目标
### 1.1 业务背景
- 当前问题描述
- 业务价值

### 1.2 项目目标
- 核心目标
- 可量化指标

### 1.3 范围界定
- 包含内容
- 不包含内容

## 2. 需求分析
### 2.1 功能需求
### 2.2 非功能需求
- 性能要求
- 安全要求
- 可用性要求

## 3. 技术方案
### 3.1 整体架构
- 架构图
- 模块说明

### 3.2 技术选型
| 方向 | 选型 | 理由 |
|------|------|------|
| 框架 | React 19 | ... |

### 3.3 详细设计
- 核心模块设计
- 接口设计
- 数据结构设计

### 3.4 方案对比（如适用）
| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|

## 4. 风险评估
| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|

## 5. 里程碑与排期
| 阶段 | 内容 | 时间 | 负责人 |
|------|------|------|--------|

## 6. 附录
- 参考资料
- 术语表
```

**技术方案评审要点：**

| 维度 | 检查项 |
|------|--------|
| 完整性 | 是否覆盖所有需求？边界条件是否考虑？ |
| 可行性 | 技术上是否可实现？资源是否足够？ |
| 扩展性 | 是否考虑未来扩展？是否过度设计？ |
| 性能 | 是否满足性能要求？是否有性能瓶颈？ |
| 安全 | 是否考虑安全问题？是否有漏洞？ |
| 成本 | 开发成本是否合理？维护成本如何？ |

### 2. 如何进行技术方案评审？

**评审流程：**

```
1. 方案准备（作者）
   └── 完成方案文档
   └── 准备演示材料
   └── 提前发送给评审人

2. 方案宣讲（15-30 分钟）
   └── 背景和目标
   └── 核心设计
   └── 风险和应对

3. 问答环节（30-60 分钟）
   └── 评审人提问
   └── 作者解答/记录

4. 评审结论
   └── 通过
   └── 条件通过（需修改后确认）
   └── 不通过（需重新设计）

5. 跟进闭环
   └── 修改方案
   └── 更新文档
   └── 确认通过
```

**评审问题清单：**

```markdown
## 架构设计
- [ ] 架构是否清晰？模块划分是否合理？
- [ ] 依赖关系是否明确？是否存在循环依赖？
- [ ] 是否考虑了高可用和容灾？

## 技术选型
- [ ] 选型理由是否充分？是否有更好的选择？
- [ ] 团队是否熟悉所选技术？学习成本如何？
- [ ] 技术成熟度和社区活跃度如何？

## 详细设计
- [ ] 接口设计是否合理？参数是否完整？
- [ ] 数据结构是否满足需求？是否有冗余？
- [ ] 异常处理是否完善？

## 性能和扩展
- [ ] 是否有性能瓶颈？如何优化？
- [ ] 是否支持水平扩展？
- [ ] 未来需求变化时，改动成本如何？

## 安全
- [ ] 是否有安全漏洞？
- [ ] 敏感数据如何处理？
- [ ] 权限控制是否到位？
```

## 二、技术选型

### 3. 如何进行技术选型决策？

**技术选型决策框架：**

```
┌─────────────────────────────────────────────────────────────┐
│                     技术选型决策流程                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 明确需求                                                 │
│     └── 功能需求是什么？                                     │
│     └── 非功能需求（性能、安全、可用性）是什么？              │
│     └── 约束条件（时间、预算、团队）是什么？                  │
│                                                              │
│  2. 候选方案调研                                             │
│     └── 列出所有可选方案                                     │
│     └── 初步筛选（排除明显不符合的）                         │
│                                                              │
│  3. 评估对比                                                 │
│     └── 制定评估维度和权重                                   │
│     └── 每个维度打分                                         │
│     └── 计算加权得分                                         │
│                                                              │
│  4. 原型验证（如需要）                                       │
│     └── 关键功能 POC                                         │
│     └── 性能测试                                             │
│                                                              │
│  5. 决策输出                                                 │
│     └── 选型结论                                             │
│     └── 理由说明                                             │
│     └── 风险和应对                                           │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**评估维度示例：**

```markdown
## 前端框架选型评估

| 维度 | 权重 | React | Vue | Solid |
|------|------|-------|-----|-------|
| 生态成熟度 | 20% | 5 | 4 | 3 |
| 性能 | 15% | 4 | 4 | 5 |
| 学习曲线 | 15% | 3 | 5 | 4 |
| 团队熟悉度 | 20% | 5 | 3 | 2 |
| 招聘难度 | 10% | 5 | 4 | 2 |
| TypeScript 支持 | 10% | 5 | 5 | 5 |
| 长期维护 | 10% | 5 | 5 | 4 |
| **加权得分** | 100% | **4.5** | **4.15** | **3.4** |

### 结论
选择 React，理由：
1. 团队已有 React 经验，无需额外学习成本
2. 生态最成熟，组件库和工具链丰富
3. 招聘市场人才充足
```

### 4. 技术选型时如何避免常见陷阱？

| 陷阱 | 描述 | 避免方法 |
|------|------|----------|
| 追新求异 | 盲目追求新技术 | 考虑技术成熟度和团队掌握程度 |
| 过度设计 | 为不存在的需求设计 | 聚焦当前需求，适度预留扩展 |
| 忽视成本 | 只看技术不看成本 | 综合考虑开发、学习、维护成本 |
| 从众心理 | 别人用什么我就用什么 | 结合自身情况独立判断 |
| 锤子思维 | 熟悉什么就用什么 | 客观评估各方案优劣 |
| 忽视退出成本 | 不考虑迁移难度 | 评估切换成本和锁定风险 |

**反思问题清单：**

```markdown
- 如果这个技术 3 年后不再维护，我们怎么办？
- 团队核心成员离职后，剩下的人能维护吗？
- 如果性能不达标，有优化空间吗？
- 如果选错了，切换成本有多大？
```

## 三、Code Review

### 5. 如何进行有效的 Code Review？

**Code Review 检查清单：**

```markdown
## 功能正确性
- [ ] 代码是否实现了预期功能？
- [ ] 边界条件是否处理？
- [ ] 异常情况是否考虑？

## 代码质量
- [ ] 代码是否清晰易读？
- [ ] 命名是否合理？
- [ ] 是否有重复代码？
- [ ] 函数是否过长？（建议 < 50 行）
- [ ] 复杂度是否过高？

## 设计
- [ ] 设计是否合理？是否过度设计？
- [ ] 是否符合项目的架构规范？
- [ ] 依赖是否合理？

## 性能
- [ ] 是否有明显的性能问题？
- [ ] 是否有不必要的计算或请求？
- [ ] 大数据量场景是否考虑？

## 安全
- [ ] 是否有 XSS、CSRF 等安全漏洞？
- [ ] 敏感数据是否正确处理？
- [ ] 权限检查是否到位？

## 测试
- [ ] 是否有对应的测试用例？
- [ ] 测试覆盖是否充分？
- [ ] 边界情况是否测试？

## 文档
- [ ] 必要的注释是否添加？
- [ ] API 变更是否更新文档？
```

**Review 评论示例：**

```markdown
## 好的评论示例

### 提供建议而非命令
❌ "这里必须改成 useMemo"
✅ "考虑到这个计算比较耗时，建议使用 useMemo 缓存结果，避免重复计算"

### 解释原因
❌ "这样写不对"
✅ "这里直接修改 state 会导致 React 无法检测变化，建议使用展开运算符创建新对象"

### 提供替代方案
❌ "这段代码太复杂了"
✅ "这个函数有点复杂，可以考虑拆分成几个小函数，比如：
- `validateInput()` 处理输入验证
- `transformData()` 处理数据转换
- `saveData()` 处理数据保存"

### 区分严重程度
🔴 [Blocker] 这里有内存泄漏，必须修复
🟡 [Suggestion] 建议使用 Optional Chaining 简化代码
🟢 [Nit] 这个变量名可以更清晰一些
```

### 6. 如何建立团队 Code Review 文化？

**Review 规范：**

```markdown
## Code Review 规范

### 1. 提交要求
- PR 大小控制在 400 行以内
- 每个 PR 只做一件事
- 提交前自己先 Review 一遍
- 填写清晰的 PR 描述

### 2. Review 要求
- 24 小时内完成 Review（工作日）
- 至少 2 人 Approve 才能合并
- 关键改动需要 Tech Lead 参与

### 3. 评论规范
- 使用标签区分优先级：[Blocker] [Suggestion] [Nit] [Question]
- 批评代码而非批评人
- 给出建设性建议

### 4. 回复规范
- 及时回复评论
- 解释修改原因或不修改的理由
- 标记已处理的评论

### 5. 合并规范
- 所有评论都已处理
- CI 检查全部通过
- 使用 Squash Merge 保持历史清晰
```

## 四、技术债务管理

### 7. 什么是技术债务？如何识别和管理？

**技术债务类型：**

| 类型 | 描述 | 示例 |
|------|------|------|
| 设计债务 | 架构设计不合理 | 组件耦合严重、缺乏抽象 |
| 代码债务 | 代码质量差 | 重复代码、复杂函数、缺少注释 |
| 测试债务 | 测试覆盖不足 | 无单元测试、关键路径未覆盖 |
| 文档债务 | 文档缺失或过时 | 无 API 文档、README 过时 |
| 依赖债务 | 依赖版本过旧 | 安全漏洞、兼容性问题 |
| 基础设施债务 | 工具链落后 | 构建慢、部署复杂 |

**技术债务评估矩阵：**

```
                     修复成本
                低    中    高
           ┌─────┬─────┬─────┐
       高  │  1  │  2  │  3  │  优先处理
  影响     ├─────┼─────┼─────┤
  程度 中  │  4  │  5  │  6  │  计划处理
           ├─────┼─────┼─────┤
       低  │  7  │  8  │  9  │  低优先级
           └─────┴─────┴─────┘
```

**技术债务管理流程：**

```markdown
1. 识别
   - 代码审查时记录
   - 团队定期讨论
   - 使用工具扫描

2. 记录
   - 技术债务清单
   - 描述问题和影响
   - 估算修复成本

3. 评估
   - 影响程度
   - 修复成本
   - 优先级排序

4. 处理
   - 纳入迭代计划
   - 分配专项时间（如每周 20%）
   - 结合功能开发顺带处理

5. 预防
   - 代码规范
   - Code Review
   - 自动化检查
```

## 五、项目管理

### 8. 如何进行项目估时和排期？

**估时方法：**

| 方法 | 描述 | 适用场景 |
|------|------|----------|
| 专家判断 | 基于经验估算 | 熟悉的任务 |
| 类比估算 | 参考类似项目 | 有历史数据 |
| 分解估算 | 拆解后逐项估算 | 复杂任务 |
| 三点估算 | (乐观+4×最可能+悲观)/6 | 不确定性高 |
| 故事点 | 相对大小估算 | 敏捷开发 |

**估时最佳实践：**

```markdown
## 估时步骤

1. 需求澄清
   - 确保理解需求
   - 识别隐藏需求
   - 明确验收标准

2. 任务拆解
   - 拆到 1-2 天的粒度
   - 识别依赖关系
   - 标记风险点

3. 估算时间
   - 开发时间
   - 联调时间
   - 测试修复时间
   - Buffer（20-30%）

4. 评审确认
   - 团队评审估时
   - 识别遗漏
   - 调整不合理估算

## 常见问题
- 忘记联调时间
- 低估沟通成本
- 未考虑并行开发
- 忽略技术学习时间
```

**排期表示例：**

| 任务 | 负责人 | 估时 | 开始 | 结束 | 依赖 | 状态 |

| 技术方案 | 张三 | 2d | 1/2 | 1/3 | T1 | ✅ |

| 测试修复 | 全员 | 2d | 1/11 | 1/14 | T4 | ⏳ |

## 六、团队协作

### 10. 如何与后端、产品、设计高效协作？

**与后端协作：**

```markdown
## 接口协作流程

1. 需求评审后，前后端对齐接口需求
2. 后端输出接口文档（Swagger/OpenAPI）
3. 前端评审接口文档
4. 确定 Mock 方案
5. 并行开发
6. 联调测试

## 接口规范约定
- RESTful 风格
- 统一错误码
- 分页、筛选、排序规范
- 时间格式（ISO 8601）
- 枚举值定义

## 沟通机制
- 接口变更及时通知
- 联调问题及时沟通
- 定期 Sync 会议
```

**与产品协作：**

```markdown
## 需求阶段
- 参与需求评审，提供技术可行性建议
- 识别需求不明确的地方，及时澄清
- 评估工作量，协商优先级

## 开发阶段
- 有疑问及时沟通，不要自己猜
- 阶段性演示，获取反馈
- 变更需求走流程

## 验收阶段
- 引导产品按场景验收
- 记录并确认问题
- 明确修复优先级
```

**与设计协作：**

```markdown
## 设计交接
- 设计稿交接会议
- 标注规范（间距、字号、颜色）
- 交互说明（动效、状态）
- 切图资源

## 开发中
- 疑问及时沟通
- 技术限制提前说明
- 还原度走查

## 设计系统
- 建立组件库
- Design Token 同步
- 设计开发一致性
```

### 11. 如何处理跨团队依赖和阻塞？

**依赖管理：**

```markdown
## 识别依赖
1. 项目启动时梳理依赖关系
2. 标记关键依赖和风险
3. 制定应对计划

## 跟踪依赖
- 依赖跟踪表
- 每日站会同步

## 处理阻塞
1. 尝试自己解决（Mock、临时方案）
2. 找对方负责人协调
3. 升级到双方 Leader
4. 必要时调整排期或方案
```

**常见问题及回答框架：**

```markdown
## Q: 说一个你解决的最有挑战的技术问题

S: 在 XX 项目中，我们遇到了首屏加载时间超过 8 秒的问题
T: 我需要将首屏时间优化到 3 秒以内
A: 我做了以下优化：
   1. 分析瓶颈：使用 Lighthouse 和 Performance 分析
   2. 代码分割：按路由懒加载，减少首屏 JS 体积
   3. 资源优化：图片压缩、使用 WebP、懒加载
   4. 缓存策略：配置强缓存和 CDN
   5. 服务端优化：开启 Gzip、HTTP/2
R: 最终首屏时间降到 2.1 秒，用户流失率降低了 15%

## Q: 说一个你与同事产生分歧的经历

S: 在技术方案评审时，我和后端同事在接口设计上有分歧
T: 我认为应该使用 GraphQL，他认为应该用 REST
A: 
   1. 我先听取了他的观点和理由
   2. 我们列出了各自方案的优缺点
   3. 我们做了一个小型 POC 验证
   4. 最终我们综合考虑团队技术栈，选择了 REST + BFF
R: 项目按时上线，后来他也认可这个方案是合适的

## Q: 说一个你失败的经历

S: 我曾经主导了一次大型重构，结果延期了两周
T: 原计划两周完成老代码到新架构的迁移
A: 
   1. 我低估了历史代码的复杂度
   2. 没有充分识别隐藏的依赖
   3. 过于乐观，没有预留 buffer
R: 虽然最终完成了重构，但延期影响了其他项目
   教训：
   - 重构前要充分调研
   - 大重构要分阶段进行
   - 估时要考虑风险 buffer
```
